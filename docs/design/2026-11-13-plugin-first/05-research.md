# Plugin-first workflow architecture research

**Checked:** 2026-11-13
**Purpose:** Compare Python plugin and workflow patterns for a modular RAG CLI. This note records primary-source facts separately from design inference. It makes no benchmark or state-of-the-art claims.

## Recommendation

Use a small, explicit workflow runner built around **typed phase contracts, chains, branches, and explicit reducers**. Keep each capability independently importable and testable; discover separately installed capability packages through Python package entry points. Keep the core runner ignorant of RAG provider implementations.

Do not adopt a general workflow framework as the runtime yet. Python `Protocol` types plus `importlib.metadata.entry_points()` cover the present extension boundary. Add a hook manager only if the host later needs many lifecycle hooks or third parties need to intercept those hooks.

This is an architectural inference from the stated CLI constraints and the frameworks' documented shapes, not a measured comparison.

## Pattern comparison

| Pattern | Verified documentation | Fit for this CLI | Decision |
|---|---|---|---|
| **Python `Protocol` + package entry points** | `typing.Protocol` expresses structural interfaces; the Python Packaging User Guide documents declaring named entry-point groups and discovering/loading them through `importlib.metadata.entry_points()`. [Typing](https://docs.python.org/3/library/typing.html#typing.Protocol) · [Plugin discovery](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/) | Contract and discovery are separate: core can type-check a capability without importing a provider, then load installed providers by declared group/name. Small runtime surface; external packages can own provider code. | **Adopt.** Define a narrow phase/capability protocol and stable versioned input/output contracts. Discover package entry points only at the application boundary. |
| **pluggy** | A host declares hook specifications; plugins register hook implementations with `PluginManager`; incompatible implementations fail registration. Hooks can return multiple results and the host may select a subset of plugins. [pluggy docs](https://pluggy.readthedocs.io/en/latest/) | Strong for host lifecycle extension and interception. It is not itself a workflow graph or typed phase-data model; hook ordering and result aggregation become additional contracts. | **Do not use as core orchestrator now.** Reconsider if real extension needs emerge around host lifecycle events. Use entry points to discover plugins independently of hook invocation. |
| **Haystack components and pipelines** | Components are reusable classes with named inputs/outputs and can run standalone or in wired pipelines; pipeline connections are validated; routers represent conditional routing. [Components](https://docs.haystack.deepset.ai/docs/components) · [Pipeline construction](https://docs.haystack.deepset.ai/docs/creating-pipelines) · [Routers](https://docs.haystack.deepset.ai/docs/routers) | Closest packaged analogue to typed components and branches. It brings a RAG framework's pipeline/runtime concepts where this project already owns phase contracts and CLI I/O laws. | **Reference pattern only.** Borrow explicit input/output and branch validation ideas; avoid a runtime dependency until a concrete feature needs Haystack integration. |
| **Apache Hamilton** | Regular Python functions in modules become graph nodes; function parameters define dependencies; the driver builds the graph and computes only requested outputs. Hamilton describes transformations as reusable outside the framework. [Overview](https://hamilton.dagworks.io/en/latest/main/) · [Drivers](https://hamilton.dagworks.io/en/latest/reference/drivers/) | Good model for phase-independent pure transformations and inspectable data dependencies. Its function-derived DAG fits acyclic work; the CRAG retry cycle needs separate control-flow semantics. | **Borrow function/module decoupling; do not use as the loop controller.** Could be reevaluated for an offline acyclic subgraph if the project needs graph planning or lineage. |
| **LlamaIndex Workflows** | A workflow is event-driven and step-based: typed events connect steps; branches and loops are explicit, and the workflow validates produced/consumed event reachability. [Workflow introduction](https://developers.llamaindex.ai/python/llamaagents/workflows/) · [Branches and loops](https://developers.llamaindex.ai/python/llamaagents/workflows/branches_and_loops/) | Closest documented analogue to explicit branching, retry loops, and typed handoff. It is async-first and adds its own workflow/event/context runtime. | **Borrow the explicit event/branch/retry model; do not take the dependency yet.** Keep this CLI's simpler chain/branch executor and validated phase payloads. |

## Proposed composition boundary

- **Core runner:** owns phase grouping, contract validation, execution order, branches, and reducers. Plugins remain phase-independent; a phase group consumes declared inputs and returns declared outputs.
- **Chains:** an ordered sequence where the prior output satisfies the next phase's input contract. Preserve the existing CLI-to-CLI pipe behavior as a supported adapter, not the only execution model.
- **Branches:** name each branch and declare its input contract and terminal output. The selected v1 design runs declared branches and joins explicitly; arbitrary predicates and cycles are not part of the core runtime.
- **Reducers:** define how fan-out results rejoin (for example, ordered concatenation or score-based selection) and validate reducer input/output types. No generic “merge anything” behavior.
- **Capability plugins:** define structural Python protocols in the core contract package. Provider packages implement them and register an entry point under a project-owned group. Resolve and validate plugins at startup; fail with the missing name or contract mismatch rather than silently substituting a provider.
- **External packages:** provider/model integrations stay in installable packages; core does not import those optional packages. This preserves independent distribution and avoids making every provider a core dependency.

The runner/phase/reducer shape above is a **design recommendation**, not a claim that any cited framework guarantees this exact architecture. Entry-point metadata discovery is supported by the Python Packaging User Guide; contract versioning, validation policy, and reducers remain project-owned decisions.

## Diagnostics lanes

The requested diagnostics split remains two decoupled modules: ordinary logging and custom error reporting. Each module should own a named standard-library logger and independently configurable sinks for a file, human-readable `stderr`, and an OpenTelemetry Protocol (OTLP) exporter. Keep each lane independently switchable and allow both modules to run together.

**Primary verified OpenTelemetry evidence:**

- The Logs specification/API/SDK/protocol are marked stable at the specification level, but the OpenTelemetry Python status table marks Python Logs as **Development**. Python's logs example warns that `opentelemetry.sdk._logs` APIs may change in minor/patch releases without backward-compatibility guarantees. Do not call the Python implementation stable. [Spec status](https://opentelemetry.io/docs/specs/status/) · [Language status](https://opentelemetry.io/status/) · [Python logs SDK warning](https://github.com/open-telemetry/opentelemetry-python/blob/main/docs/examples/logs/README.rst)
- The current Python example uses `opentelemetry-instrumentation-logging`'s `LoggingHandler`; the old `opentelemetry.sdk._logs.LoggingHandler` is deprecated/moved. The official bridge turns stdlib records into OTel records. When `LogRecord.exc_info` is present, current handler source maps exception type, message, and formatted stack trace to semantic-convention attributes. [Official example](https://github.com/open-telemetry/opentelemetry-python/blob/main/docs/examples/logs/example.py) · [Handler source](https://github.com/open-telemetry/opentelemetry-python-contrib/blob/main/instrumentation/opentelemetry-instrumentation-logging/src/opentelemetry/instrumentation/logging/handler.py) · [Contrib changelog](https://github.com/open-telemetry/opentelemetry-python-contrib/blob/main/CHANGELOG.md)
- Official Python exporter docs document both OTLP HTTP/protobuf and gRPC packages. The current verified PyPI releases checked here are SDK `1.45.2`, HTTP exporter `1.45.2`, gRPC exporter `1.45.2`, and logging integration `0.66b2`. PyPI marks the three core packages Production/Stable; the logging integration is Beta and the listed release is a pre-release. [Python exporter docs](https://opentelemetry.io/docs/languages/python/exporters/) · [SDK](https://pypi.org/project/opentelemetry-sdk/) · [HTTP exporter](https://pypi.org/project/opentelemetry-exporter-otlp-proto-http/) · [gRPC exporter](https://pypi.org/project/opentelemetry-exporter-otlp-proto-grpc/) · [Logging integration](https://pypi.org/project/opentelemetry-instrumentation-logging/)
- The official Python log example attaches a `BatchLogRecordProcessor` and gRPC `OTLPLogExporter` to a `LoggerProvider`. The exporter docs describe HTTP/protobuf and gRPC as the two supported OTLP transport choices. Both can be wired as processors, with per-module configuration deciding whether to enable one or both.
- Keep `logging.StreamHandler(sys.stderr)` as the **human console lane**. `ConsoleLogRecordExporter` is an OpenTelemetry SDK exporter for structured record/debug output, not the human-readable operator formatter. The current documented spelling is `ConsoleLogRecordExporter`; older versions used `ConsoleLogExporter` before 1.39.0. [Python instrumentation/logging example](https://opentelemetry.io/docs/languages/python/instrumentation/)

**Design inference:** give each diagnostics module its own explicitly supplied `LoggerProvider` and `LoggingHandler`, so it need not race to set the process-global default provider. Use module-specific logger namespaces and avoid accidental propagation to duplicate handlers. Attach file and human stderr handlers independently from the OTel processor. This gives each module its own file/stderr/OTLP switches and permits simultaneous operation. If trace exception events are also required, that is a separate traces concern; the evidence above verifies log exception attributes, not span-event behavior.
